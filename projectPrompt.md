1. Product and first release

lastDSMRlogger shall read P1 telegrams from a smart meter, validate and decode them through parserDSMR, and make recent telegrams visible in a single-page web application served by the logger. The SPA shall have two views, Settings and Telegrams. The first release shall retain a short, bounded history in RAM and persist configuration across restarts. Long-term logging through the meter rings and their graphs and tariff fields are in scope via the meter store; MQTT publication of the latest accepted telegram is in scope via the Settings view (see sections 4 and 8). SD-card storage, cloud services, and legacy API compatibility are outside this release.

The project shall target the ESP32-S3 on the TFT LCD Display EC11 Piggyback Board v3 using native ESP-IDF 6.0.2. The application and integration code shall use C with plain structs, enums, functions, Allman braces, lowerCamelCase identifiers for functions and variables, and English comments. The web interface shall use local HTML, CSS, and JavaScript assets. The hardware target shall reserve the display, encoder, buttons, SD, and I²C pins. Use mrWheel's `esp32_s3_piggyback` component from [esp32-s3-Piggyback](https://github.com/mrWheel/esp32-s3-Piggyback) for board integration. Read the API documentation in that component's `README.md` and use its documented API; do not implement direct board/peripheral driving. The two required screens are browser views. An on-device TFT interface is outside this release except for showing debug lines what the device is doing like
- show browser active screen names
- receive telegram on P1
- start WiFi portal with IP adres
- when connecting to WiFi show SSID and IP-address
- other debug information

3. P1 input and board configuration

The P1 data signal shall pass through a P1 interface that provides the appropriate signal conditioning and a 3.3 V-compatible signal at the ESP32-S3 input. The setup documentation shall identify the interface, wiring, signal polarity, and how the meter’s P1 request signal is enabled. The first release shall use an externally enabled request signal. RX polarity shall be set by the documented interface configuration at build time. The cumulative counters published on the P1 port are never negative: a telegram that publishes a negative counter is refused by the meter store (the rings keep their previous values until a sound telegram arrives, while the raw record stays retained for inspection).

The production receiver shall use a hardware UART separate from the console. Its RX GPIO shall be selected from the board’s J5 connector. The initial selectable set shall be GPIO10, 38, 39, 40, 41, 42, 47, and 48, subject to the resources actually enabled by the board configuration. GPIO43 and GPIO44 shall remain reserved for UART0. The application shall validate the selected pin against the same board allowlist whether the selection arrives through the SPA or the API. On first boot, or if saved settings cannot be loaded, reception shall await a valid configuration.

4. Settings view

|Setting         |Required behavior                                                                                                                                                                         |
|----------------|------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------|
|P1 RX GPIO      |Select an eligible J5 input and show its GPIO number.                                                                                                                                     |
|Country         |Select the country code from the available parser profiles.                                                                                                                               |
|Protocol version|Select a supported profile for the chosen country. Persist the stable profile ID. Display the human-readable protocol version and keep it separate from the version reported by the meter.|
|M-Bus channels  |Show channels 1–4. Each channel shall default to **Auto** and shall offer **Disabled** and explicit device types supported for the selected profile.                                      |
|MQTT            |Enter the broker IP/URL, broker port, user, password, top topic and broadcast interval. An empty broker or interval 0 (no broadcast) keeps publication off; otherwise the most recently accepted telegram is published to `<top topic>/telegram` every interval. |
|Tariffs         |Enter the manual prices (Tariff 1/2 Delivered, Tariff 1/2 Received, Tariff Gas Delivered) in EUR; every tariff field shall accept up to five decimals. |
|Network         |Enter the hostname announced to DHCP and mDNS and the fixed IP as its last octet only (empty or 0 means plain DHCP; the network part comes from the granted lease).                        |

The settings service shall obtain built-in IDs through dsmrProfileListIds() and country and timing metadata through dsmrProfileLookup(). The baseline includes nl.dsmr.4.0, nl.dsmr.4.2, nl.dsmr.4 (4.0/4.2 selection), nl.dsmr.5.0, be.emucs.1.x, and be.emucs.2.1. The SPA shall use the choices returned by the settings service. UART settings, telegram framing, version checks and CRC policy shall follow the selected profile and the parser’s defaults.

In Auto mode, the application shall use the device type reported in the channel’s 0-n:24.1.0 field. Explicit expected types shall be submitted through dsmrParserConfig.mbusDevices and mbusDeviceCount. The parser emits DSMR_DIAG_MBUS_TYPE_MISMATCH after an accepted telegram if the published type contradicts the configured one. The logger shall also detect a missing published type from the decoded fields. Disabled is a logger display setting. An explicit selection shall act as an expected type. A mismatch or missing type shall be visible in decoded diagnostics. The application shall preserve source data and shall only present a channel as the configured device type when the reported type matches. Disabled channels shall be omitted from the decoded summary while their lines remain visible in the raw telegram. A channel without a reading shall be shown as unavailable when applicable. A measured zero shall remain distinguishable from an unavailable reading. Submeter measurement timestamps and units shall be displayed as supplied by the parser. M-Bus data shall come from the P1 telegram.

Save shall validate and apply the complete configuration as one operation. The settings service shall store the complete versioned configuration in ESP-IDF NVS. Any receiver restart shall discard a partial frame and initialize the new parser profile before consuming further bytes. If activation or persistence fails, the service shall restore the previous configuration and report the failure in the SPA. A successful save shall show the active configuration and current receive state. Previously captured records shall retain the country, profile and decoded data associated with their capture.

5. Telegrams view

The view shall update automatically, show the latest accepted telegram by default, and allow the user to select a recent telegram for inspection. New arrivals shall leave the user’s selected telegram in view while it is available. The interface shall report when a previously selected telegram has aged out and allow the user to return to the latest telegram.

Each retained record shall contain a sequence number, receive time, active profile, reported version, validation status, and the exact raw data received for the accepted frame. The raw view shall preserve original line endings and the trailer, and shall display text without interpreting it as HTML. A decoded summary shall show available electricity measurements and enabled M-Bus channels from that same telegram. Receive time, meter time, and M-Bus measurement time shall remain distinct. If wall-clock time is unavailable, receive age or uptime shall be shown explicitly.

The view shall distinguish input awaiting configuration, input awaiting data, an accepted telegram, a stale last reading, and a receiver or parser error. Rejected candidates shall update diagnostics without replacing the last accepted telegram. Diagnostics shall include available reasons and receive counters. RAM limits shall be explicit and shall accommodate at least two maximum-sized supported telegram records in the documented target configuration. The oldest record shall be evicted first. Slow or disconnected browser clients shall have no effect on UART reception.

6. Integration and build

• The receive path shall use dsmrUartStart() and dsmrUartStop(), setting dsmrUartConfig.rxPin from active settings and requestGpio to -1 for external request. Parser initialization shall use dsmrParserInit() with caller-owned workspace sized by dsmrParserWorkspaceSizeNeeded(). Configuration changes shall stop and join the receive task before reinitializing the parser and starting the UART with the new settings. The runtime shall preserve the previous saved configuration until the new receiver is ready and restore it if the change fails. The adapter shall report UART overflow and framing errors as data loss. The inspected adapter uses polling without a UART event queue, so explicit reporting of these events shall be added or verified in the production dependency.
• The logger requires a public, read-only raw byte view and length on the accepted dsmrTelegramResult. At the baseline, the result exposes decoded fields and the decoder modifies the framing buffer in place. The parser shall preserve a bounded copy of the complete received frame before in-place decoding, including every original line ending and trailer byte. It shall expose that copy only with the accepted event, with a lifetime through the callback, and include its storage in workspace sizing. The logger shall copy that view and the decoded result into its history. Framing and CRC shall remain the responsibility of parserDSMR.
• One receive task shall own the receiver and parser state. Callback data needed by the SPA shall be copied within its documented lifetime. HTTP handlers shall read consistent snapshots and shall avoid holding receive-side locks during network writes.
• ESP-IDF esp_http_server shall serve the SPA and its API from the same origin. The API shall expose active settings and valid choices, settings updates, reception status and diagnostics, recent telegram metadata, and individual telegram details and raw bytes. The SPA shall transfer only recent metadata and telegrams it needs. All assets shall work over the local network without an external service.
• Use MichMich's `esp-idf-wifi-provisioner` component for connecting with saved Wi-Fi credentials and captive-portal fallback when credentials are not yet provisioned or the saved network cannot be joined. Document the first-boot provisioning flow without requiring firmware recompilation. The logger shall continue processing P1 telegrams while Wi-Fi is disconnected and shall serve the SPA again after reconnecting. The project shall document the local URL or how to find the device IP.
• The deliverable shall include the ESP-IDF project files, the pinned parser dependency, embedded SPA assets, and a README with build, flash, monitor, Wi-Fi setup, P1 wiring, and hardware verification instructions. The normal build path shall use idf.py set-target esp32s3, idf.py build, and idf.py -p PORT flash monitor.

7. Wi-Fi link recovery

The Wi-Fi link is essential to the product: it is the route to the SPA, the API, the telnet console, the SMB share and MQTT publication. The application shall establish the station connection through the provisioner and shall then keep a once-established link up through access-point interruptions, IP configuration failures and stalled application sessions. `recoveryWiFi.md` is the design guide; the following requirements are normative.

1. Startup and handoff. The recovery manager (one owner task: the Wi-Fi task) registers its persistent station and IP event handlers before the provisioner starts connecting, and runtime reconnect actions stay disabled until the provisioner's connected callback hands the link over by message. The manager reads the live association and IP state when it handles the handoff: the first GOT_IP may have arrived before it, and the link may already have dropped since.
2. Connection ownership. One task owns the desired station state, the current connection attempt and the retry timer. Event callbacks stay short: they copy the signal and its disconnect reason into a queue and the owner task serialises reconnects, deadlines and session starts. While the provisioning library is retrying (initial attempts and the captive portal), that library keeps execution of those retries and the manager does not duplicate them.
3. Live state, not latched state. Runtime link status comes from the manager's association and IP picture, not from the provisioner's connection flag (which latches the initial success) nor from its IP getter (which can report a stale address over an outage). The SPA status and the telnet `status` answer the Wi-Fi questions from the manager's live state.
4. Reconnect policy. After a runtime disconnect the manager schedules one `esp_wifi_connect()` attempt per due time using the credentials already configured in the driver, with exponential backoff from a short base (2 s) to a cap (60 s) plus jitter, one attempt in flight, checked request results, and the backoff reset as soon as the station has a usable address again.
5. Separate deadlines. Association and IP assignment have separate deadlines (15 s), each logged so the log names the phase in which an attempt stalled. Association that yields no address re-requests DHCP once; a second expiry breaks the association and starts a fresh attempt through the retry policy.
6. Idempotent service re-arm. Every network-dependent service (SNTP once per boot, hostname and mDNS announcement, fixed-IP pin, MQTT network gate, SPA server, telnet console, SMB share) is armed through the same regular startup path on the first join and on every recovery, and each owner guards itself so duplicate signals cannot create duplicate sessions or listeners. Client sessions go down with the link and are re-armed when the address returns.
7. Escalation and observation. When attempts keep failing while the retry policy itself runs healthy, the manager escalates with a rate-limited adapter restart (at most one per 10 minutes) run through the connection manager and logged. State transitions, disconnect reasons, retry phases and attempt numbers are logged; credentials and tokens stay out of the log. A periodic reconciliation compares the manager's picture with the driver and netif state so a lost event cannot stall recovery.
8. Provisioning stays provisioning. Saved credentials are retained during runtime outages; the captive portal remains the path for setup and reconfiguration, and the manager keeps its reconnect actions disabled while the portal owns the station. A boot while the access point is unavailable therefore ends in the portal and needs the portal (or a reboot once the access point is back).

8. Control channels and telnet console

The device shall allow exactly one operator per control channel: one web browser `/ws` session and one telnet session may be active at the same time, each holding its own control slot. Ordinary HTTP asset and API requests are not operators; the single-client rule governs control traffic only. A new client only ever displaces the previous owner of its own channel and never touches the other one: a second browser page ends the first page without disturbing the telnet session, and a second telnet client ends the first session without disturbing the browser page. The client that reports itself holds its channel slot; when another client of the same channel reports itself, the slot moves to the new client and the previous owner is ended. An evicted web page shall first receive a takeover message on its WebSocket and then have its socket closed, and shall show a popup stating that control was taken over by another browser page together with a button that reloads the page and claims control back; while that popup is open the page's WebSocket auto-reconnect is halted so control never bounces back on its own. An evicted telnet session shall receive a clear text farewell on its own session before that socket is closed. The slot is released when a socket actually closes, so an ordinary disconnect and reconnect is never mistaken for a takeover. The rule follows the single-`/ws`-client design of the reference radioProject (checked on the first data frame, cleared in the httpd `close_fn`).

The device shall run a telnet console server on port 23, started together with the SPA once the station has joined. It shall serve exactly one telnet session at a time. The console shall greet with the firmware version and the peer address, prompt for commands with line editing (backspace), perform minimal telnet negotiation (server-side echo, incoming IAC sequences skipped), and answer commands: `help`, `status`, `version`, `state`, `telegrams`, `telegram [<seq>]`, `raw [<seq>]`, `power`, `showring {month|days|hours}`, `ring2csv {month|days|hours}`, `populate {hours|days|months} [overwrite|update]`, `filesystem {list|delete|rename|show}`, `settings {save|load}`, `sync`, `verbose {0,1,2,3}`, `restart` and `quit` (`ringfile` remains a synonym of `showring hours`). `telegram` and `raw` without a sequence show the most recently accepted telegram. Commands are case-insensitive and may be shortened to any leading part that names exactly one command. `state` reports the device state block: the copyright line, hostname, firmware version with build date, compile stamp and component versions, free and minimum free heap, largest free block, PSRAM free and total, chip ID and model, SDK version, CPU frequency, running app partition size with used and free sketch space, flash chip size, speed and mode, and the LittleFS volume size. `filesystem list` shall report the LittleFS storage volume: every file on the mounted volume with its size, the total capacity and the free space (the former `store` command, renamed). `filesystem delete` shall ask "delete what file: ", and only when the typed file exists ask "Are you sure (N/y)?", removing it on a typed `y` (or `yes`) and cancelling otherwise. `filesystem rename` shall ask "rename old name: " (an unknown file is reported and cancels), then "new name: " (an existing name is reported and cancels), then "Are you sure (N/y)?", renaming on a typed `y` (or `yes`) and cancelling otherwise. `filesystem show` shall ask "show what file" and print the file's contents skipping every control character except tab, carriage return and line feed, which are shown as they are. `settings save` shall ask "save settings to" and write every settings field to that file on the volume root as one plain ascii ini (one `[section]` header per settings group — `[p1port]`, `[display]`, `[mbus]`, `[mqtt]`, `[network]`, `[store]` and `[tariffs]` — and one `key = value` line per field, text quoted, numbers plain): an empty answer writes them to `YYMMDDhhmm-settings.ini` (the stamp is the device clock at the export moment), a typed name that does not end in `.ini` gets the suffix appended. `settings load` shall ask "load what settings file", read that file and store every value back into NVS. `status` shall report reception state, RX GPIO and data source, profile and interval, uptime, receive counters, last diagnostics and error, device clock, Wi-Fi SSID and IP, and the current control owner. `showRing {month|days|hours}` shall list the stored records of one meter ring file (hours, days or months; hours is the default). `raw <seq>` shall write the exact accepted bytes with their original line endings and trailer. `ring2csv {month|days|hours}` shall ask for the csv file name to write (an empty answer keeps the default `YYMMDDhhmm-<name>.csv`, stamped with the device clock at the export moment, a plain name gets the `.csv` suffix) and write the selected ring at the volume root newest period first. `sync` shall make the store task commit all three ring files at once and restart the configured rfs synchronisation interval from that moment. A bare `[Enter]` (an empty line) prints the `help` command list; an empty line keeps its answer role while a command question is open (populate file, ring2csv name, restart confirmation, the filesystem delete/rename/show questions and their confirmations, the settings save/load questions). `verbose {0,1,2,3}` shall set console event reporting: 0 prints no debug lines, 1 the event lines and the error lines, 2 also the telegram-related lines and 3 also the chatty info and warning lines and a mirror of the serial console log (every info, warning and error line the monitor shows reaches the telnet session as well, without ever blocking the logging task); `help` shall show the level currently set on the command line itself (for instance `verbose 2 {0,1,2,3}`), and `verbose` without an argument shall show the usage together with the current level; with reporting on the console prints one event line per notable background event — ring file synchronisations, MQTT connections, incoming MQTT tariff messages and tariff schedule updates (via MQTT or the API) and settings updates through the API — with the telegram level adding the per-publish line and the top level the per-download line; each line is framed by its wall-clock time and its reason kind, for instance `[hh:mm:ss Event]`, `[hh:mm:ss Error]`, `[hh:mm:ss Telegram]`, `[hh:mm:ss Info]` or `[hh:mm:ss Warning]` (the stamp reads `--:--:--` until the clock is synchronised); event lines carry no blank padding — each ends on the re-printed console prompt (when the session shows one), and they are written without blocking the reporting task and never interleave into a command answer. `restart` shall ask "are you sure (N/y)?" and, only after a typed `y` (or `yes`), first synchronise the ring files (the `sync` commit of all three rings, waited for) and only then reboot the device; an empty line or anything else cancels. Console output shall never block P1 reception, and the console task shall not draw on the TFT board (the board mutex can be held across a repaint window); telnet connect and disconnect are reported on the serial console log.

9. RFS history editor

The SPA's System group holds an **Edit** view that reads and revises one meter ring through a bounded typed API; the browser never writes an `.rfs` file or supplies a filesystem path (see the `ringEdit` entry of the `VIEWS` registry, `loggerStoreEditorSnapshot()`/`loggerStoreApplyRingEdits()` in `components/logger_store` and `GET`/`POST /api/v3/ringedit` in `components/logger_web`). The code is the specification below.

Opening the view always shows an empty screen with empty, loading and error states: Hours, Days and Months are mutually exclusive radio buttons that only name the ring (mapped to the existing `hours.rfs`, `days.rfs` and `months.rfs` selectors), and nothing is read from the device until **[Load]** fetches the snapshot. **[Cancel]** discards the pending edits of the shown ring, drops a load still in flight and returns the view to its empty state; the `.rfs` is left exactly as it was. Typed drafts survive switching the radio group and leaving the view and reappear when that ring is loaded again; only Cancel (for the shown ring) or a successful save clears them. **Save** sits below the table and stays disabled until the draft holds valid edits.

The table lists every retained record in logical (ring append) order, newest first — the staged newest RAM record included, and the ring's own bucket order is kept even when keys are corrupt. Each row shows the period key and the five cumulative readings read-only — electricity import T1 and T2, export T1 and T2 (kWh) and gas (m³) — with a consumption input next to each reading, the three editable period amounts Import €, Export € (shown as a credit, negative values allowed) and Gas € (EUR, two decimals), and the stored network costs as a separate read-only historical figure. The newest record of the open period is locked: the logger rewrites it with every store snapshot, so it is shown read-only (this is also the guard that keeps the periodic tariff calculator from overwriting saved edits — an open period is editable only after it closes). The oldest row has no older baseline, so its consumption inputs are unavailable. Invalid values render red with a field-level tooltip, modified inputs carry a subtle tint (reverting to the snapshot value removes it), and repaired keys and recalculated readings mark pending; a channel whose every period is zero reads as unavailable.

An edit to row A's use keeps A's current draft reading and sets `reading(B) = reading(A) − entered use` on the immediately older row B; other channels and all other rows keep their readings. Explicit consumption edits stay separate from implied differences and are rebuilt newest to oldest per channel, so the result never depends on typing order and removing an edit recomputes from the snapshot plus the remaining edits. Period amount edits are stored verbatim — history is never repriced with today's rates — and survive neighbouring consumption changes. Cumulative readings must be strictly descending per recorded channel across adjacent rows; equal readings (genuine zero use and unused registers included) and reversed readings are invalid, explained in the UI, and block Save; nothing is silently adjusted to satisfy the rule. Readings may carry a negative sign: a normalised history imported through populate (for example after a meter exchange) keeps the descent running below zero, and such records stay valid under the same rule — only values read in from the P1 port shall never be negative (section 3), while the populate import and the editor accept them. The browser pre-validates (finite, range and precision, adjacency) and the store re-validates every candidate value server-side as the single source of truth.

Period keys are repaired by comparison with the expected sequence, stepped back one calendar period at a time from a trustworthy newest-period anchor (the store's authoritative period information, device timezone, never the browser clock) across month and year boundaries, leap days and daylight-saving transitions. An illegal, duplicated, gapped or out-of-order key shows the original in red with the proposed replacement as a preview; each proposed key is verified legal and unique for the ring's schema, and repairs take effect only when the Save lands. When the anchor cannot be trusted the view names why and key repairs stay blocked until it can be resolved.

`GET /api/v3/ringedit?ring=<hours|days|months>` answers the snapshot (capacity, retained count, store-running and clock-synced flags, the open-period key, the anchor verdict and one entry per record with index, key, timestamp, checksum pin, staged and locked flags and the key-repair preview). `POST /api/v3/ringedit` carries `{ring, count, newestKey, records}` with at most `LOGGER_STORE_EDITOR_MAX_EDITS` (64) rows, each pinned by its snapshot row checksum (and, for a consumption edit, the older row's checksum), in a body bounded by 16 KB; malformed values, unknown or locked rows, an oldest-row consumption edit, duplicate edit targets, oversized or stale requests are refused with a specific error and leave the ring untouched. A Save is one transaction for the selected ring only: the store task rebuilds the complete candidate (repaired keys and edited payloads together), validates it before anything is written, writes it as a journal ring file (`<ring>.rfs.edit.tmp`), reopens and verifies it on storage, and publishes through two atomic LittleFS renames (live → backup, journal → live), answering success only after the new ring is durably in place. An interrupted Save is recovered deterministically at startup before any ring opens or is resized, yielding either the complete old or the complete new ring — never an empty replacement of an unreadable one — and the editor locks keep snapshots and publishes serialised against background commits, rollovers and populate imports while normal logging continues with the page open. A response lost after the commit is recovered by a plain reload; the same corrections cannot be applied twice because every later Save re-pins the reloaded snapshot. Editing one granularity leaves the other two rings, the ring metadata and the exports untouched, and a saved ring reports itself once on the verbose console event channel.

10. Acceptance criteria

1. The project builds with ESP-IDF 6.0.2 for ESP32-S3. After flash and documented Wi-Fi setup, the device serves both SPA views.
2. Saving a supported GPIO, country/profile, and M-Bus configuration activates the complete configuration and survives a power cycle. Invalid pins, mismatched country/profile pairs, and unsupported M-Bus settings produce feedback and preserve the active configuration.
3. Representative valid Dutch and Belgian fixtures travel through the normal receive path and appear in the SPA. The raw response matches the supplied accepted frame byte for byte. The decoded summary matches parser output, including units and missing values.
4. Invalid CRC, truncated input and input received during a profile change leave the most recent accepted record intact. Reception recovers on the next complete valid frame.
5. M-Bus Auto, Disabled, and expected-type mismatch behavior is verified with more than one channel. Raw data remains available for every channel in an accepted frame.
6. At the fastest supported telegram cadence, the history remains bounded and a slow browser does not stall reception. A network disconnect and reconnect preserves reception and restores access to the web interface. With the access point unavailable the station retries at a rate-limited pace and rejoins with its stored credentials without a reboot once the access point returns; after the rejoin every network service (SPA, telnet console, SMB share, MQTT publication) is reachable again.
7. On the physical target, a conditioned P1 signal on a selectable J5 pin is received with the documented interface settings. The selected RX GPIO and console operate together and the board’s reserved peripheral pins remain available for their assigned functions.
8. With the SPA open and holding its web slot, a telnet client connecting runs alongside it: the browser keeps receiving its pushed updates and is never popped up by telnet activity. A second telnet client displaces the first: the evicted session shows its clear takeover farewell and closes, while the browser stays active. A second browser page displaces the first: the evicted page shows the takeover popup with the take-control-back button, stops auto-reconnecting and its pushed updates stop, while the telnet session stays active; pressing the button reclaims the web slot and evicts the other page. With a channel slot free, that channel can operate, and a normal disconnect/reconnect is not blocked by a stale token.
